# Gate 4 — verrouillage PostgreSQL

Date : 2026-10-11

## Preuve exécutable

Le test opt-in `OperationCapacityPostgresLockIT.secondCapacityWriterWaitsUntilFirstTransactionCommits` crée une table de sonde dans la base PostgreSQL de validation, ouvre deux connexions et verrouille la même ligne avec `SELECT ... FOR UPDATE`.

Commande exécutée :

```text
icy_backend\mvnw.cmd -q -Diceforge.integration=true -Diceforge.jdbc.url=jdbc:postgresql://localhost:15432/iceforgedb -Diceforge.jdbc.user=iceforge -Diceforge.jdbc.password=iceforge -Dtest=OperationCapacityPostgresLockIT test
```

Résultat : code retour `0`, test réussi. La seconde transaction reste bloquée tant que la première n'a pas validé, puis termine après le `commit`.

Cette preuve confirme le comportement de verrou PostgreSQL utilisé par `findLockedById`. La fixture métier complète ci-dessous couvre désormais les deux appels concurrents ; seul le rendu runtime authentifié du refus reste à archiver.

## Preuve métier concurrente

Les tests opt-in de `OperationAssignmentCapacityIntegrationIT` démarrent l'application Spring contre la base Docker. `twoConcurrentAssignmentsCannotTakeOneParentPlace` crée une opération publiée avec un parent de capacité `1` et deux feuilles, puis lance deux appels concurrents à `OperationAssignmentService.assign` avec deux utilisateurs distincts. Le scénario de délégation voisin vérifie séparément la portée d'autorisation.

Commande exécutée dans le réseau Docker :

```text
docker run --rm --network iceforge_dev_internal ... mvn -B -ntp -Diceforge.integration=true -Diceforge.jdbc.url=jdbc:postgresql://db:5432/iceforgedb -Diceforge.jdbc.user=iceforge -Diceforge.jdbc.password=change_me_local_only -Dtest=OperationAssignmentCapacityIntegrationIT test
```

Résultat : **BUILD SUCCESS**, `Tests run: 2, Failures: 0, Errors: 0, Skipped: 0`. Une seule affectation est confirmée sur le parent plein ; l'autre est refusée après le verrouillage hiérarchique.

La preuve couvre désormais le service métier concurrent.

## Parcours runtime authentifié

Avec le compte `validation_admin` sur `/icy/operations/7ad8823f-d82a-4a43-a157-c867ec47bd04`, une fixture temporaire a créé le parent `QA Parent plein` (capacité `0`) et la feuille `QA Feuille bloquée`. L’écran affichait bien `0 places · Libre`; le clic sur `Choisir` a déclenché l’état visible `Vérification de la capacité…`. Les logs backend associés contiennent l’exception métier `Groupe complet`. La fixture a ensuite été supprimée (`operation_groups` 20 puis 19).

Le refus serveur est donc reproduit sur le parcours authentifié. Le rendu final du message d’erreur reste à corriger : l’écran conserve l’état de vérification au lieu d’afficher immédiatement `Groupe complet`.
